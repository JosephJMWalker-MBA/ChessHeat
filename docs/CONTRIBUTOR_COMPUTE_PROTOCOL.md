# ChessHeat Contributor Compute Protocol v1

## Status

This document defines the first public-compute contribution boundary for ChessHeat.

It does **not** authorize any currently blocked scientific experiment, open TEST data, relax an existing preregistration, change any frozen semantic contract, or permit community results to be merged into an authoritative result merely because they were produced with ChessHeat code.

The governing invariant remains:

> **The mathematics needs to earn the color.**

Contributor compute exists to make replication, prospective data acquisition, and separately governed extension studies easier to perform and easier to audit.

## Why this exists

ChessHeat has reached a point where outside contributors may be able to add meaningful scientific capacity without needing to redesign the project.

A contributor may have:

- a faster CPU or GPU;
- more RAM;
- a machine they can leave running for days;
- chess-engine expertise;
- interest in independently reproducing a result;
- access to additional compute for prospectively defined work packets.

The useful scientific object is not "someone ran the code."

The useful object is:

```text
declared protocol
+ declared inputs
+ declared software identities
+ declared scientific parameters
+ declared execution-only parameters
+ complete machine-readable provenance
+ resumable execution history
+ hashed outputs
+ verification verdict
```

The contributor wrapper therefore creates provenance automatically while it runs.

## Three contribution classes

Contributor results must be classified before execution.

### A. `REPLICATION_EXACT`

The contributor repeats an already-defined work unit with the same scientific object.

Examples:

- same root identities;
- same input artifacts;
- same Stockfish build and engine settings;
- same source/target budgets;
- same learner and seed;
- same stopping rule;
- same statistical semantics.

Different hardware may be used if the governing protocol does not make hardware a scientific variable.

Purpose:

- independent reproducibility;
- detection of hidden hardware/runtime assumptions;
- confirmation that deterministic artifacts reproduce where identity is expected.

A replication result is **replication evidence**. It does not silently become an additional observation in the original statistical analysis.

### B. `PROSPECTIVE_SHARD`

The contributor executes new work units that were assigned before their outputs were seen under a separately frozen acquisition packet.

Examples:

- prospectively selected additional roots;
- a new corpus shard generated by a declared sampling rule;
- additional positions collected under the same measurement procedure.

Purpose:

- grow a versioned evidence corpus;
- test generalization in a separately governed extension;
- support future protocols.

A prospective shard is **not appended to an already-frozen experiment by default**. Any future analysis that combines old and new shards must explicitly define and freeze that combined population.

### C. `COMPUTE_EXTENSION`

The contributor intentionally changes a scientific computation budget or instrument setting.

Examples:

- deeper Stockfish node budgets;
- more training roots;
- more epochs;
- another engine version;
- a materially different search or learner budget.

Purpose:

- extension research;
- robustness studies;
- instrument sensitivity;
- larger-compute follow-up questions.

A compute extension is a **new protocol object**, not "better data" for the frozen experiment.

## Hardware-adaptive execution, protocol-invariant science

The wrapper may adapt execution mechanics to the contributor's machine when the packet explicitly allows those fields.

Examples of execution-only parameters:

- number of parallel independent workers;
- queue depth;
- CPU affinity;
- process scheduling;
- log flushing cadence;
- non-scientific checkpoint frequency.

These may improve throughput without changing what is measured.

The wrapper must not silently tune scientific parameters.

Examples of scientific parameters that remain packet-controlled:

- root population;
- source or target engine version;
- node/depth/time search budget;
- Threads / Hash when frozen by the protocol;
- candidate policy;
- representation operator;
- learner family;
- seed set;
- epoch budget;
- early-stopping rule;
- split assignment;
- analysis rule;
- acceptance threshold.

The rule is:

```text
hardware-adaptive execution != hardware-adaptive science
```

## Work packets

A contributor does not invent a run from memory.

They receive a versioned work packet.

A packet must identify:

- packet schema;
- packet ID;
- contribution class;
- authorization status;
- approved scientific commit SHA;
- files whose bytes are bound to that scientific commit;
- input identities;
- engine identity requirements when applicable;
- scientific parameters;
- permitted runtime-adaptive fields;
- work-unit IDs;
- command argv for each work unit;
- timeout/liveness policy;
- required output paths;
- whether exact output identity is expected.

Packets should be committed to the ChessHeat repository before public use.

A packet with status other than `AUTHORIZED_FOR_CONTRIBUTOR_EXECUTION` may be inspected and preflighted, but the wrapper must refuse to execute it.

## Contributor execution lifecycle

```text
obtain official packet
    ->
clone / checkout compatible ChessHeat repository
    ->
run wrapper preflight
    ->
verify repository + bound-file identities
    ->
verify required engine binary identity
    ->
capture hardware/runtime environment
    ->
execute assigned work units
    ->
persist stdout/stderr + attempts
    ->
resume after interruption if needed
    ->
verify required outputs
    ->
hash complete bundle
    ->
submit bundle for project-side verification
```

The contributor should not need to manually construct a scientific log.

The wrapper's execution bundle is the log.

## Repository integrity

A contributor run must begin from a clean tracked and untracked working tree unless a future packet explicitly defines a different isolation mechanism.

The wrapper records:

- current repository HEAD;
- approved scientific SHA;
- packet SHA-256;
- bound-file verification result;
- Git status;
- Python version;
- OS and architecture;
- available CPU count;
- memory information where available;
- installed ML/runtime identity where available.

The current HEAD may be newer than the approved scientific SHA only when:

1. the approved SHA is an ancestor of HEAD; and
2. every packet-bound scientific file is byte-for-byte identical to the approved commit.

This permits a later contributor wrapper or documentation commit to coexist with an older frozen scientific implementation without mutating that implementation.

## Engine identity

When a packet requires Stockfish or another external executable, the packet should bind the executable by cryptographic digest whenever practicable.

The wrapper records:

- executable path supplied by the contributor;
- SHA-256 of the executable bytes;
- expected digest;
- version string if the packet defines a safe version-query method.

A version label alone is insufficient when byte identity matters.

## Long-running execution and resumption

Contributor work may run for hours or days.

Every work unit must have a stable `work_unit_id`.

The wrapper stores each attempt separately and only creates an accepted work-unit record after:

- process completion;
- exit code acceptance;
- required outputs exist;
- required outputs are regular files under the work-unit directory;
- output hashes are recorded.

On restart:

- valid accepted work units are reused;
- missing work units are executed;
- a corrupted or internally inconsistent accepted record causes fail-closed behavior rather than silent recomputation inside the same bundle.

A contributor can start a new bundle when a prior bundle is damaged.

Interruption history is evidence and should remain visible.

## Duplicate computation

Two contributors running the same exact packet is not necessarily waste.

For `REPLICATION_EXACT`, duplicated work is valuable when the protocol expects reproducibility.

Possible outcomes:

```text
same inputs + same scientific configuration + different hardware
    -> identical result where identity is expected
```

supports reproducibility.

```text
same inputs + same scientific configuration + different hardware
    -> scientifically material divergence
```

is itself a research finding requiring investigation.

Possible causes include:

- engine nondeterminism;
- threading effects;
- numerical backend differences;
- hidden runtime state;
- filesystem/resumption differences;
- undeclared dependencies.

## Bundle contents

A normal contributor bundle should contain, at minimum:

```text
packet.json
preflight_report.json
environment.json
work_units/
  <work_unit_id>/
    attempts/
      0001/
        stdout.log
        stderr.log
        attempt.json
    accepted_result.json
run_manifest.json
bundle_index.json
```

Additional experiment outputs remain beneath their work-unit directories.

`bundle_index.json` contains SHA-256 identities for the final files in the bundle, excluding the index itself.

## Submission and admission

A submitted bundle is **candidate evidence**.

Project-side admission is a separate act.

Before a bundle can be used scientifically, the project must decide:

- does the packet class permit the proposed use?
- did the packet have execution authorization?
- did preflight pass?
- do bound-file and engine identities match?
- is the bundle internally complete?
- do output schemas and scientific invariants pass?
- is the result a replication, a new shard, or an extension?
- does any frozen protocol authorize combining it with another dataset?

The contributor wrapper does not grant scientific authority.

## Public compute ladder

ChessHeat can support progressively deeper participation:

1. submit a position or counterexample;
2. curate or classify fixtures;
3. reproduce a small known reference unit;
4. execute an exact replication packet;
5. contribute a prospectively assigned shard;
6. execute a separately frozen larger-compute extension;
7. help design a new formal study.

A useful eligibility pattern is:

> reproduce a small reference packet first; then claim larger new work packets.

This tests the contributor environment before expensive compute is assigned.

## Credit

When a community contribution materially informs a research question, replication result, dataset extension, or published finding, the public research note should credit the contributor in a manner consistent with their requested public identity.

Credit does not imply scientific agreement with every interpretation submitted by the contributor.

## Security boundary

Packets are executable instructions.

Contributors should run packets only from a trusted ChessHeat repository/commit they have intentionally chosen to trust.

The wrapper executes argv lists without a shell, but trusted repository code can still perform arbitrary actions available to that user account.

Do not run unfamiliar contributor packets with elevated privileges.

## Current project boundary

This v1 protocol defines the infrastructure.

It does **not** itself authorize the currently blocked CP-only downstream production experiment for community execution.

A future packet for that experiment must be created only after its own implementation, hostile re-audit, and authorization gates permit contributor execution.

Until then, contributor-compute development should use synthetic or explicitly non-scientific reference packets.

## Acceptance criterion for v1

Contributor compute v1 is ready for pilot use when:

- packet validation is strict;
- preflight records repository and environment identity;
- scientific bound files can be verified against an approved commit;
- runtime-adaptive fields are explicitly constrained;
- long work units can resume without losing accepted results;
- each attempt preserves stdout/stderr and timing;
- required outputs are hashed;
- bundle verification fails closed on tampering;
- no currently blocked experiment is made executable merely by this infrastructure.
